= The Gradle Plugin
:navtitle: The Gradle Plugin

The `net.benelog.spidersense` plugin puts `-javaagent:` on the JVM that Gradle forks for `bootRun` or `run`, so an application starts under Spider Sense with no path and no JVM argument in the build file.
Spider Sense is a `-javaagent`, so it has to be on the command line of the JVM that runs the application.
Gradle forks that JVM itself for `bootRun` and `run`, and the option has to reach the forked JVM, not Gradle's own.
This page covers only getting the jar onto that command line.
The jar's own options are in xref:configuration.adoc[Configuration], and the modes it runs in are in xref:modes.adoc[The Three Modes].

[source,groovy,subs="attributes+"]
----
plugins {
    id 'org.springframework.boot' version '4.1.1'
    id 'net.benelog.spidersense' version '{project-version}'
}
----

[source,bash]
----
./gradlew bootRun
----

That is the whole setup.
The application starts under Spider Sense, named after the project, and the UI is at http://127.0.0.1:4000.

The plugin resolves the jar from Maven Central through the project's repositories, as `{project-group}:spider-sense:{project-version}` at the plugin's own version.
`mavenCentral()` therefore has to be among them, as it is in every Spring Boot project.
The plugin itself is a plain Gradle plugin, published to Maven Central with its marker.
The Gradle Plugin Portal proxies Maven Central, so the default `pluginManagement` finds the plugin.

The plugin applies nothing else and configures nothing it was not asked to.
It works the same with the `application` plugin's `run` task.
A project with neither Spring Boot nor `application` gets the `spiderSense` block and the three tasks, and no task gets the agent.

A build that cannot take a new plugin puts the argument on the task itself, with an absolute path to the jar:

[source,groovy,subs="attributes+"]
----
tasks.named('bootRun') {
    jvmArgs '-javaagent:/absolute/path/to/spider-sense-{project-version}.jar', '-Dotel.service.name=spring-orders'
}
----

[#applying]
== What applying it does

. Creates the `spiderSense` extension, which is the `spiderSense { }` block.
. Creates the `spiderSense` configuration, resolvable and not consumable, non-transitive, with one default dependency: `{project-group}:spider-sense:<version>`, where `version` is the block's property and defaults to the plugin's own version.
A dependency added to the configuration by the build replaces the default.
A project in a checkout of this repository uses the jar it just built this way: `dependencies { spiderSense project(path: ':spider-sense-agent', configuration: 'senseJar') }`.
. Attaches to every `JavaExec` task whose name is in `attachTo` (default `bootRun`, `bootTestRun`, `run`) by adding a `CommandLineArgumentProvider` to the task's `jvmArgumentProviders`.
The provider contributes `-javaagent:<jar>` first, then one `-Dspidersense.<key>=<value>` per property of the block that has a value.
The jar is a declared input of the task, so a project dependency on it is built first.
A task that is not in `attachTo`, or a run with `spiderSense.enabled` false, gets nothing: no argument, no jar resolution.
The plugin adds a provider and never edits `jvmArgs`, so the task's own `jvmArgs` stay as the build wrote them.
The arguments are computed when the task runs, so a `spiderSense { }` block anywhere in the build file, before or after `tasks.named('bootRun')`, is seen.
. Registers the tasks `spiderSense`, `spiderSenseInit` and `spiderSenseCheck` in the group `spider sense`.

Nothing here touches the Gradle daemon.
A `jvmArgumentProvider` reaches only the forked JVM.
That is the reason to use the plugin rather than `JAVA_TOOL_OPTIONS`.
`JAVA_TOOL_OPTIONS` reaches every JVM the command starts, including the daemon, which then tries to host a Spider Sense of its own on port 4000.

[#block]
== The block

Every property is a lazy Gradle `Property`.
An unset property leaves the jar's own default in place.
xref:configuration.adoc#properties[Configuration] lists the jar's defaults.

[cols="1,1,1,3",options="header"]
|===
| Property
| Type
| Default
| Becomes

| `enabled`
| `Boolean`
| `true`
| nothing is attached when `false`; the project property `spiderSense.enabled` (`-PspiderSense.enabled=false`, or `=true`) wins over the block

| `version`
| `String`
| the plugin's version
| the version of `{project-group}:spider-sense` the default dependency names

| `jar`
| `RegularFile`
| unset
| the jar to attach instead of resolving one; the project property `spiderSense.jar` (`-PspiderSense.jar=/path/to/spider-sense.jar`) wins over the block

| `attachTo`
| `Set<String>`

| the names of the `JavaExec` tasks that get the agent

| `configFile`
| `RegularFile`
| unset

| `service`
| `String`
| `project.name`
| `-Dspidersense.service=`, which is `otel.service.name` unless that is set already

| `port`
| `Integer`

| `-Dspidersense.port=`

| `host`
| `String`
| unset (`127.0.0.1`)

| `collector`
| `String`
| unset

| `db`

| `retentionHours`
| `Integer`

| `slowRequestMs`
| `Long`

| `slowQueryMs`
| `Long`
| unset (`100`)

| `open`
| `Boolean`
| unset (`false`)
| `-Dspidersense.open=`: open the browser at startup

| `appPackages`
| `List<String>`
| unset
| `-Dspidersense.app.packages=`, the list joined with commas

| `ignoreEndpoints`
| `List<String>`
| unset (the jar's default list)
| `-Dspidersense.ignore.endpoints=`, the list joined with commas; an empty list set explicitly (`ignoreEndpoints = []`) passes an empty value, which ignores nothing

| `retentionSpans`
| `Long`
| unset (`1000000`)
| `-Dspidersense.retention.spans=`

| `Long`

| see <<check-task,Check as a build step>>
| the rules of the `spiderSenseCheck` task
|===

[#jar-resolution]
The plugin looks for the jar in this order: the project property `spiderSense.jar`, then the block's `jar`, then the single file of the `spiderSense` configuration.
When a task that needs the jar runs, a configuration with more than one file, or none, is an error that names the configuration.

The block sets only `spidersense.*` properties.
The launcher also reads a `spider-sense.properties` in the project directory, because the forked JVM's working directory is the project's.
`configFile` names a different properties file.
The block's `-D` properties win over the file either way (xref:configuration.adoc#properties-file[the properties file]).
Every `otel.*` property of the OpenTelemetry agent goes on the task as usual, and the block and the task's `jvmArgs` combine:

[source,groovy]
----
spiderSense {
    port = 4001
    slowQueryMs = 50
    appPackages = ['com.acme.orders']
}

tasks.named('bootRun') {
    jvmArgs '-Dotel.instrumentation.jdbc-datasource.enabled=true'
}
----

[#switching]
== Switching it off and on

`./gradlew bootRun -PspiderSense.enabled=false` runs the application bare.
`spiderSense { enabled = false }` with `-PspiderSense.enabled=true` reverses that: the plugin stays in the build, and attaches only when you pass the property.
An `enabled` of `false` is the same as not applying the plugin, except that the block and the tasks are still there.

[#tasks]
== The tasks

`spiderSense` runs the jar exactly as `java -jar spider-sense.jar` would, so both the standalone server and the xref:cli.adoc[CLI] are one Gradle task away in a project that never checked out this repository:

[source,bash]
----
./gradlew spiderSense                                   # the standalone collector + UI; Ctrl-C stops it
./gradlew -q spiderSense --args="findings --since=start" # the CLI; -q keeps Gradle's own lines out
./gradlew -q spiderSense --args="check --max-n-plus-one=0"
----

The `spiderSense` task is a `JavaExec` with the jar as its only class path, `net.benelog.spidersense.launcher.SpiderSenseMain` as its main class, and no dependency on compiling the project.
The block's `spidersense.*` properties are passed to it as they are to the application, so a standalone started this way listens where the block says.
Its `service` is passed as well, and a standalone ignores it: the standalone runs inside no application, so its `status` names no embedded service.
When the block names a `collector`, a `host` or a `port`, it also sets the environment variable `SPIDERSENSE_URL` to the base URL they imply, which is `collector` when set and otherwise `http://<host>:<port>` with the defaults filled in.
A CLI command therefore asks the Spider Sense the application is sending to rather than the default port.
When the block names none of them, the variable stays unset and the CLI's own default applies.
That default is the URL the task's `spidersense.*` properties imply, so a port set in `configFile` or in `spider-sense.properties` is followed too.
A CLI exit code other than `0` fails the task, and Gradle's failure message names that code as the process's exit value.
`./gradlew` itself exits `1` for every failed task, so a script cannot tell the CLI's codes `1` to `4` apart through the task.
A script that branches on the code runs `java -jar` on the jar itself, and `spiderSenseCheck` fails with a message of its own for each outcome of `check` (<<check-task,Check as a build step>>).

`spiderSenseInit` runs `init --dir=<the project directory> --jar=<the jar>`.
It writes the Spider Sense block into the project's `CLAUDE.md` and installs the skills into `.claude/skills/`, as xref:agent-skill.adoc#init[The Agent Skill] describes.
The jar path it writes is where Gradle resolved the jar to.
For a Maven Central jar that is a file under `~/.gradle/caches/`, which stays valid until the version changes.
Run it again after a `version` bump.

[#check-task]
== Check as a build step

`spiderSenseCheck` runs the CLI's xref:check.adoc[check] with the rules of the `check { }` block and fails the build when the verdict is `fail`:

[source,groovy]
----
spiderSense {
    check {
        since = 'start'          // the default: since the application was last started
        maxP95Ms = 300
        maxNPlusOne = 0
        maxErrors = 0
    }
}
----

[source,bash]
----
./gradlew bootRun &                  # or the test task forwarding to a standalone, as below
./gradlew test spiderSenseCheck
----

[cols="1,1,3",options="header"]
|===
| Property
| Type
| Becomes

| `since`
| `String`
| `--since=`; default `start`

| `until`
| `String`
| `--until=`

| `service`
| `String`
| `--service=`; default the block's `service`

| `endpoint`
| `String`
| `--endpoint=`

| `maxP95Ms`
| `Long`
| `--max-p95-ms=`

| `maxErrors`
| `Long`
| `--max-errors=`

| `maxErrorRate`
| `Double`
| `--max-error-rate=`

| `maxQueriesPerRequest`
| `Double`
| `--max-queries-per-request=`

| `maxSlowQueries`
| `Long`
| `--max-slow-queries=`

| `maxNPlusOne`
| `Long`
| `--max-n-plus-one=`

| `maxLogErrors`
| `Long`
| `--max-log-errors=`

| `minApdex`
| `Double`
| `--min-apdex=`

| `failOnNoRequests`
| `Boolean`
| default `true`: exit code `3` (no request in the window) fails the build too, because a check that judged nothing is not a pass
|===

`spiderSenseCheck` runs the jar as the `spiderSense` task does, with `check` and those arguments.
It asks the Spider Sense the block implies, through `SPIDERSENSE_URL` or the CLI's own default as <<tasks,The tasks>> describes.
It prints the check's text rendering.
Exit code `1` fails the build with `Spider Sense check failed`.
Exit code `3` fails it with `Spider Sense check had no request to judge`, unless `failOnNoRequests` is `false`.
Exit code `2` or `4` fails it with `Spider Sense check could not run (exit <n>)`.
The CLI's own message reaches the build log first in every case.

With no rule set the CLI's defaults apply: `maxErrors=0`, `maxNPlusOne=0`, `maxP95Ms=<slow.request.ms>`.
`-PspiderSense.check.since=before` overrides `since` for one run.
`spiderSenseCheck` depends on no other task, because producing the traffic it judges is the build's job, as in the setup of <<tests,Tests>>.

[#tests]
== Tests

The test task is not attached by default.
A test JVM is short-lived and may be forked several times, and several embedded servers would fight over one port.
To measure tests, forward them to a standalone Spider Sense: add `test` to `attachTo` and set `collector`, one line each:

[source,groovy]
----
spiderSense {
    attachTo.add('test')
    collector = 'http://127.0.0.1:4000'
}
----

[source,bash]
----
./gradlew spiderSense &                           # once
./gradlew -q spiderSense --args="mark before"
./gradlew test --tests '*OrderServiceTest'
./gradlew -q spiderSense --args="findings --since=before"
----

With `collector` set, `bootRun` forwards too.
That is what you want when the tests and the running application should land in one Spider Sense.

[#multi-project]
== Two applications, several modules

Each module that applies the plugin gets its own block, so in a multi-project build the applications are configured where they are:

[source,groovy]
----
// orders/build.gradle
spiderSense { port = 4001 }
// bookstore/build.gradle
spiderSense { port = 4000 }
----

When one calls the other and the trace should be one trace, run a standalone and xref:modes.adoc#forwarding[forward] both:

[source,groovy]
----
spiderSense { collector = 'http://127.0.0.1:4000' }
----

[#devtools]
== Spring Boot devtools

A devtools restart replaces the application's classes inside the same JVM.
The agent stays attached, the embedded UI keeps running, and the restarted classes are instrumented like the first ones.
There is nothing to configure.

[#local-jar]
== A jar that is not on Maven Central

A version that is not published yet, or a jar built from a checkout, is attached in one of three ways:

[source,bash,subs="attributes+"]
----
./gradlew bootRun -PspiderSense.jar=/home/me/spider-sense/spider-sense-agent/build/libs/spider-sense-{project-version}.jar
----

[source,groovy]
----
spiderSense {
    jar = file('/home/me/tools/spider-sense.jar')
}
----

[source,groovy]
----
// In this repository: the jar the build just made, built before bootRun runs.
dependencies {
    spiderSense project(path: ':spider-sense-agent', configuration: 'senseJar')
}
----

`./gradlew publishToMavenLocal` in this repository publishes both the jar and the plugin to `~/.m2`.
`mavenLocal()` in `repositories` and in `pluginManagement.repositories` then makes an unreleased version resolvable like a released one.

[#configuration-cache]
== Configuration cache

The plugin is compatible with Gradle's configuration cache.
Every value is a provider, the argument provider holds no `Project`, and the jar is a `FileCollection` input.

[#coordinates]
== Coordinates

The plugin is `{project-group}:spider-sense-gradle-plugin`, with the marker `{project-group}:net.benelog.spidersense.gradle.plugin`, and resolves the jar `{project-group}:spider-sense` at its own version.
xref:install.adoc#coordinates[Installation] lists both artifacts and how they are published.

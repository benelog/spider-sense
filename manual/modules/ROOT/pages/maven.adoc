= Maven
:navtitle: Maven

Spider Sense is a `-javaagent`, and `spring-boot:run` forks the JVM that runs the application, so the option has to reach that forked JVM, not Maven's own.
There is no Spider Sense Maven plugin, because the Spring Boot Maven plugin already has the two parameters Spider Sense needs.
`agents` (user property `spring-boot.run.agents`) takes agent jars and puts each on the forked JVM as `-javaagent:`.
`jvmArguments` (`spring-boot.run.jvmArguments`) or `systemPropertyVariables` carry the `spidersense.*` properties.
Both parameters belong to `spring-boot:run` and to `spring-boot:start`, the goal that runs the application around integration tests.

[#command-line]
== Once, from the command line

[source,bash]
----
mvn spring-boot:run -Dspring-boot.run.agents=/home/me/tools/spider-sense.jar
mvn spring-boot:run -Dspring-boot.run.agents=/home/me/tools/spider-sense.jar \
    -Dspring-boot.run.jvmArguments="-Dspidersense.port=4001 -Dspidersense.service=orders"
----

Without `spidersense.service` the service is `spring.application.name`, and without that the directory of the project whose `target/classes` holds the main class, as xref:configuration.adoc#service-name[The service name] describes.
Every property the jar takes is listed in xref:configuration.adoc#properties[Configuration].

[#pom]
== In the POM

The `maven-dependency-plugin` copies the jar from Maven Central into `target/` before the application starts, and `spring-boot:run` names it in `agents`.
`spring-boot:run` runs the `test-compile` phase first, so the copy bound to the `initialize` phase has finished by then.
Put both in a profile, so `mvn spring-boot:run -Psense` is the run under Spider Sense and `mvn spring-boot:run` is the plain one:

[source,xml,subs="attributes+"]
----
<profiles>
  <profile>
    <id>sense</id>
    <properties>
      <spider-sense.version>{project-version}</spider-sense.version>
      <spider-sense.jar>${project.build.directory}/spider-sense.jar</spider-sense.jar>
    </properties>
    <build>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-dependency-plugin</artifactId>
          <executions>
            <execution>
              <id>spider-sense</id>
              <phase>initialize</phase>
              <goals>
                <goal>copy</goal>
              </goals>
              <configuration>
                <artifactItems>
                  <artifactItem>
                    <groupId>{project-group}</groupId>
                    <artifactId>spider-sense</artifactId>
                    <version>${spider-sense.version}</version>
                    <outputDirectory>${project.build.directory}</outputDirectory>
                    <destFileName>spider-sense.jar</destFileName>
                  </artifactItem>
                </artifactItems>
              </configuration>
            </execution>
          </executions>
        </plugin>
        <plugin>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-maven-plugin</artifactId>
          <configuration>
            <agents>
              <agent>${spider-sense.jar}</agent>
            </agents>
            <systemPropertyVariables>
              <spidersense.service>${project.artifactId}</spidersense.service>
              <spidersense.port>4000</spidersense.port>
            </systemPropertyVariables>
          </configuration>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>
----

A jar that is not on Maven Central goes in as a path.
Drop the `maven-dependency-plugin` execution and set `spider-sense.jar` to the file, in the profile or on the command line with `-Dspider-sense.jar=/home/me/tools/spider-sense.jar`.

[#surefire]
== Tests under Surefire

Surefire forks its own JVM and takes its options from `argLine`.
The plugin below goes into the `sense` profile's `<plugins>`, beside the other two, because the profile is where `spider-sense.jar` is defined and the jar copied.
`mvn test -Psense` then runs the tests under Spider Sense, and `mvn test` runs them plain.
Forward to a standalone Spider Sense rather than embedding one.
A test JVM is short-lived and may be forked more than once, and several embedded servers would fight over one port.

[source,xml]
----
<!-- in the sense profile, under <build><plugins> -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <argLine>-javaagent:${spider-sense.jar} -Dspidersense.collector=http://127.0.0.1:4000 -Dspidersense.service=${project.artifactId}-test</argLine>
  </configuration>
</plugin>
----

Start the standalone once before `mvn test -Psense` runs, as xref:modes.adoc#forwarding[forwarding] describes.

[#packaged-jar]
== The packaged jar

Running the packaged jar under the agent needs nothing in the POM at all:

[source,bash]
----
mvn -q package -DskipTests
java -javaagent:/home/me/tools/spider-sense.jar -Dspidersense.service=orders -jar target/orders-0.0.1.jar
----

[#cli]
== The CLI from `target/`

The CLI is the same jar, so once the `sense` profile has copied it into `target/`, you run it from there:

[source,bash]
----
java -jar target/spider-sense.jar findings --since=start
java -jar target/spider-sense.jar init            # the CLAUDE.md block and the skills
----

The CLI asks `http://127.0.0.1:4000` unless told otherwise, and it does not read the POM.
When the POM gives the application another port, add `--url=http://127.0.0.1:<port>` to each command.
Or set the port as `spidersense.port=<port>` in `spider-sense.properties` in the project directory instead, which the application and the CLI both read (xref:configuration.adoc#properties-file[The properties file]).

xref:cli.adoc[The CLI] documents every command, and xref:agent-skill.adoc#init[The Agent Skill] documents what `init` writes.

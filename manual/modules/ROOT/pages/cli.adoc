= The CLI
:navtitle: The CLI

The Spider Sense jar is also a command line: `java -jar spider-sense.jar <command>` answers a question about a window of the stored data, in Markdown made for an agent to read.

The CLI renders nothing itself.
When a Spider Sense answers at `--url`, the CLI fetches the `format=text` rendering and prints the body, so its numbers are the ones the UI shows.
When none answers, the CLI opens the H2 file in process and runs the same queries through the same renderer (<<fallback,the direct-file fallback>>).

[#invocation]
== Invocation

[source,bash]
----
java -jar spider-sense.jar <command> [arguments] [options]
----

The launcher treats a first argument that does not start with `-` as a command, and hands the whole line to the CLI inside the nested server jar, through the same `SenseClassLoader` the embedded server uses (xref:design.adoc#jar[The jar]).
The launcher itself stays dependency-free.
`--port=` and the other standalone flags still start a server, so `java -jar spider-sense.jar` with no command is the standalone UI rather than a command (xref:modes.adoc#standalone[Standalone]).

Under the Gradle plugin, the `spiderSense` task runs the same CLI, even in a project that never checked out the Spider Sense repository:

[source,bash]
----
./gradlew -q spiderSense --args="findings --since=start"
./gradlew -q spiderSense --args="check --max-n-plus-one=0"
----

`-q` keeps Gradle's own lines out of the output.
A CLI exit code other than `0` fails the task, and `./gradlew` then exits `1` whatever the code was, so only Gradle's failure message names it.
A script that branches on the <<exit-codes,exit code>> runs `java -jar spider-sense.jar` itself.
When the `spiderSense` block names a collector, a host or a port, the task also sets `SPIDERSENSE_URL` to the base URL that block implies, so the command asks the Spider Sense the application is sending to rather than the default port (xref:gradle-plugin.adoc#tasks[Tasks]).

`SPIDERSENSE_URL` names the Spider Sense to ask whenever `--url` is not given.
Without either, the `spidersense.*` properties decide: `spidersense.collector` when set, else `http://<host>:<port>` with the defaults filled in, which is `http://127.0.0.1:4000` when nothing is set.
The launcher reads xref:configuration.adoc#properties-file[the properties file] before a command runs, so a command run from the project's directory asks the Spider Sense the application in that directory sends to.

[#findings-ack-resolve]
=== findings, ack and resolve

`findings` is the primary answer: a ranked, bounded list of things worth fixing over the window.
The table is the answer, and the numbered blocks under it are the evidence, one per row in the same order.
xref:findings.adoc[Findings] has every kind with its rule and its numbers.

[source]
----

----

`ack <finding id> [--note=<text>]` accepts a finding that is known and will not be fixed now.
It is then ranked after every other finding, and its severity column reads `acked`.
`unack <finding id>` withdraws the acknowledgement, and exits `4` when there was none.
`findings --hide-acked` leaves the acknowledged findings out altogether.
The finding id is the one `findings` printed in its `id` column, and it is stable across windows (xref:findings.adoc#acknowledgements[Acknowledgements]).

`resolve <finding id> [--note=<text>]` records that a finding is fixed.
If it occurs again after that, `findings` reports it as a `regression`, severity `high`, first in the list, and `check` fails on it by default.
Until then it is ranked after every other finding, and its severity column reads `resolved`.
`unresolve <finding id>` withdraws the resolution, and exits `4` when there was none.
xref:findings.adoc#resolutions[Resolutions] says when a finding counts as back.

The `state` column says what the last restart changed: `new` for a finding the run before the restart did not have, `ongoing` for one it had, and `regressed` for a regression (xref:findings.adoc#state[State]).

[#suspect-change]
==== The suspect change

Under each code frame whose file is in the repository the CLI runs in, `findings` adds one line naming the change that last touched that line:

[source]
----
   orders.OrderService.load(OrderService.java:41)
     changed in 4743e1d (2 hours ago): Run Error Prone and NullAway in every javac
   orders.web.OrderController.show(OrderController.java:28)
     uncommitted
----

The line is indented two spaces past the frame, so a reader of the block sees it as the frame's.
It is one of three things.

* `uncommitted` when the file is in `git diff --name-only` or `git diff --cached --name-only`, or is untracked (`git ls-files --others --exclude-standard`), because a file the agent has just created is the most likely suspect of all.
It is also `uncommitted` when `git blame` says the line itself is not committed yet.
* Otherwise `changed in <hash> (<age>): <subject>`, from the commit `git blame -L <n>,<n> --porcelain` names for the frame's line: the first seven characters of its hash, its author date as an age in the largest whole unit (`45 seconds ago`, `2 hours ago`, `3 days ago`, `3 weeks ago`, `4 months ago`, `2 years ago`), and its subject.
* Nothing when the frame does not resolve under xref:configuration.adoc#source-dirs[the source roots] (xref:findings.adoc#source-lines[Source lines and the suspect change]), when the file lies outside the repository, or when `git blame` has nothing to say about the line, as for a file edited to be shorter than the frame's line.

The line answers the question an agent has first: is the line this finding points at in the change I just made.
It is off when the working directory is not in a repository or `git` cannot be run, and `--no-git` turns it off.
A `git` command that has not answered within 10 seconds is killed, with whatever it started, and what it would have said is left out.
`--json` prints the server's JSON, which never carries it.

This line is the one thing the CLI adds to an answer instead of printing what the server or the in-process renderer produced, and it has to be.
The CLI runs in the project directory, where the repository is, and the server may run elsewhere or not at all.
It is added to the text after the rendering, and left out by `--no-git` and by `--json`.
It is therefore also the one part of a findings answer that is not a function of the window alone: the age depends on when it was asked, and the verdict on the working tree.
The HTTP API and the xref:mcp.adoc[MCP] `findings` tool answer without it, since neither knows which repository the caller is working in.

[#compare]
=== compare

`compare --before=<selector> --after=<selector>` puts the window before a mark beside the window after it, endpoint by endpoint and query by query.
It takes no `--since`, because its windows are the two selectors.

The verdict is each row's first column and the worst rows sort first, so the top of each table is the answer.
xref:marks-and-compare.adoc#compare[Compare] has the verdicts and their thresholds.

[#check]
=== check

`check` turns thresholds into pass or fail, and puts the verdict in the exit code.
Every rule named on the command line is evaluated, and naming one replaces the default set.
xref:check.adoc#rules[Check] has every rule, the value it measures and its default.

[source]
----
$ java -jar spider-sense.jar check --since=before
# check  fail  2026-09-17T08:19:28+09:00 → 08:19:45  (17s, all services, 33 requests)

| rule | limit | actual | verdict | detail |
| --- | --- | --- | --- | --- |
| maxP95Ms | 500 | 1,202.5 | fail | GET /api/slow p95 1,202.5 ms over 3 calls |
| maxErrors | 0 | 2 | fail | 2 occurrences over the window |
| maxNPlusOne | 0 | 2 | fail | 2 findings: GET /api/orders/{id} runs SELECT product 5 times per request |
| maxRegressions | 0 | 0 | pass | no resolved finding came back |

$ echo $?
1
----

`--endpoint=` narrows the scope to one endpoint, by its id or by its name, and the heading names that endpoint.

[#tail-command]
=== tail

`tail` prints one line per live event as it arrives, so a request that was just sent can be watched instead of polled for.
It needs a running Spider Sense.
See <<tail,Tail>>.

[#export-command]
=== export and import

`export` writes the window as one JSON document, and `import` reads one back into a store.
See <<export-import,Export and import>>.

[#sql-command]
=== sql

`sql "<statement>"` runs one read-only statement over the schema, for a question no other command answers.
See <<sql,SQL>>.

[#init]
=== init

`init` writes the Spider Sense block into the project's `CLAUDE.md` and installs the skills into its `.claude/skills/`.
It is the one command that reads nothing: no HTTP, no database, no running Spider Sense.
It takes none of the common options, and its own are `--dir`, `--jar`, `--no-skill` and `--mcp`.
See xref:agent-skill.adoc#init[init].

[#mcp]
=== mcp

`mcp` runs the MCP server over stdio, for a host that has no shell.
It takes `--url` and `--db` and nothing else, because a window, a format and a service belong to each message of the session rather than to the command.
See xref:mcp.adoc[MCP].

[#help]
=== help

`help` prints every command, every common option, the selector forms and the exit codes.

[source]
----
$ java -jar spider-sense.jar help

| `--db=<path or jdbc url>`
| `~/db/spider-sense/sense`
| read that database directly, without asking any server

| `--json`
| off
| print the JSON of xref:api.adoc[the HTTP API] instead of the text

| `--full`
| off
| keep statements whole and expand collapsed spans

| `--hide-acked`
| off
| `findings` only: leave the acknowledged findings out instead of ranking them last

| `--no-git`
| off
| `findings` only: no <<suspect-change,suspect-change line>> under the code frames
|===

`--since` and `--until` take a time selector: a duration, epoch milliseconds, a mark name, `start` or `now`.
xref:marks-and-compare.adoc#time-selectors[Time selectors] states every form.

Three commands depart from the table.
`compare` takes no `--since`, because its windows are the two selectors, and its `--until` closes the second window.
`init` takes none of these options at all, and its own are `--dir`, `--jar`, `--no-skill` and `--mcp`.
`mcp` takes only `--url` and `--db`.

`--slow.request.ms=`, `--slow.query.ms=` and `--app.packages=` set the thresholds and the application packages in the direct-file path, where no server is there to ask.

An option a command does not take is a usage error rather than a silently ignored word, so a mistyped `--sinse` is reported rather than answered for the last 15 minutes.

[#exit-codes]
== Exit codes

[cols="1,4",options="header"]
|===
| Code
| Meaning

| `0`
| success, and `check` passed

| `1`
| `check` failed

| `2`
| usage or connection error

| `3`
| `check` had no request to judge

| `4`
| not found: a trace id, a mark name, a finding id to `unack` or `unresolve`
|===

A trace id that matches nothing prints `spider-sense: No such trace: <id>` on stderr and exits `4`, whether the answer came over HTTP or from the file.
A mark name that matches no mark also exits `4`, with a message naming the mark.
`unack` of a finding that has no acknowledgement prints `spider-sense: No such acknowledgement: <id>` and exits `4` as well.
`unresolve` of a finding that has no resolution prints `spider-sense: No such resolution: <id>` and exits `4`.

Exit code `3` means the exercise step did not reach the application, not that a fix worked.

[#fallback]
== The direct-file fallback

When nothing answers at the default URL, the CLI opens the H2 database in process, runs the same queries through the same renderer, and says so on stderr:

[source]
----
(no Spider Sense at http://127.0.0.1:4000; reading /home/me/db/spider-sense/sense.mv.db directly)
----

`AUTO_SERVER=TRUE` makes this possible (xref:storage.adoc[Storage]).
After the application has crashed and taken the UI with it, `findings --since=start` still answers.

"Nothing answers" means the connection was refused or not made within 2 seconds.
A Spider Sense that accepted the connection and has not answered within 2 minutes is busy, not gone.
The CLI then prints `spider-sense: the Spider Sense at <url> did not answer within 2 minutes` and exits `2` without reading the file, since reading it in process would be slower still.

Naming `--url` states that a server is there.
When nothing answers it, the CLI prints `spider-sense: no Spider Sense at <url> (…)` and exits `2`, rather than silently falling back to a file that may hold a different application.
`--db=<path or jdbc url>` states the opposite, where to read, and the CLI goes straight to that file without asking any server.

In that path the thresholds are the defaults, or whatever `--slow.request.ms`, `--slow.query.ms` and `--app.packages` say, since no server is there to ask.

The file must exist and carry this version's schema.
The CLI never creates a database and never upgrades one, because `AUTO_SERVER=TRUE` may have joined the database of an older Spider Sense that is still running, and recreating the tables would empty it under that server.
A missing file is exit `2` and, on stderr:

[source]
----
spider-sense: no Spider Sense database at /home/me/db/spider-sense/sense.mv.db; start an application with -javaagent:spider-sense.jar first
----

A file of another schema version is refused the same way, with exit `2` and a message naming both versions.

Six commands write rather than read, and they write in this path too: `mark`, `ack`, `unack`, `resolve`, `unresolve` and `import`.
`tail` is the one command that has no direct-file path, because there is no file to tail.

[#text-rendering]
== Text rendering

Every answer follows the same rules, so the output is small, stable and diffable.
The same data renders to the same bytes, so two answers can be diffed.

The CLI prints these renderings, and the HTTP API serves them too.
An agent-facing endpoint answers Markdown when it is asked with `format=text`, or with an `Accept` header whose first type is `text/markdown` or `text/plain`, and the response is then `text/markdown; charset=utf-8`.
JSON stays the default, and xref:api.adoc#agent-endpoints[Agent-facing endpoints] has the wire shapes.
The endpoints with a text rendering are `/api/status`, `/api/findings`, `/api/findings/\{id}`, `/api/marks`, `/api/compare`, `/api/check`, `/api/sql`, `/api/traces`, `/api/traces/\{id}`, `/api/endpoints`, `/api/queries`, `/api/queries/\{queryId}`, `/api/errors`, `/api/errors/\{errorId}`, `/api/logs` and `/api/services`.

The conventions:

* The first line is a heading naming the answer and the window, in ISO-8601 with the local offset: `# findings  2026-09-18T12:37:06+09:00 → 12:41:08  (4m 1s, all services, 2456 requests)`.
The range is rounded to the second and written in its largest units (`6s`, `2m 30s`, `15m`, `2h`), never in milliseconds.
* Lists are Markdown tables, and ids are complete: a trace id is 32 hex characters, an endpoint, query or error id 12, because they are passed back.
* A trace and `logs` are lines rather than a table, and `status` and `mark` answer in their own shape.
* Durations are milliseconds with one decimal and a thousands separator (`1,532.4 ms`), counts are integers, rates are percentages with one decimal, and an Apdex is a score with three decimals.
* A cell with nothing in it is `—`, and in `compare` the two sides of a row share one cell, `before → after`.
* A cell is one line whatever text it holds: its newlines and runs of whitespace collapse to one space, and a `|` in it is escaped, so an exception message, a note or a span name never splits a row.
* A statement is cut at 200 characters with `…`, and `--full` keeps it whole.
* Nothing in the body depends on when it was rendered, only on the window.
`now` appears only in the heading.
* An empty result says what was looked for and where, as in `no findings since 2026-09-18T12:42:26+09:00 (20s, 16 requests)`, and, when there was no request at all, how to send some: the OTLP endpoint.

[#trace-rendering]
=== A trace

A trace is an indented tree, one span per line.
The trace below crosses two example applications, `spring-orders` calling `silk-bookstore`, and the repeated `SELECT product` spans under the entry span are collapsed into one row that carries the statement:

[source]
----
# trace 09e96c4c6db157e690716c2615ffd146  2026-09-18T12:37:29.077+09:00  12.2 ms  spring-orders → silk-bookstore  20 spans, 10 db, 0 errors

offset     duration  span
0.0 ms     12.2 ms   SERVER spring-orders GET /api/orders/{id}/enriched → 200
0.7 ms     0.6 ms      INTERNAL OrderRepository.findById
0.7 ms     0.5 ms        INTERNAL Session.find orders.domain.Order
0.9 ms     0.1 ms          db SELECT orders
1.4 ms     0.0 ms      db SELECT order_line
1.6 ms     0.0 ms      db SELECT product  × 4, 0.0 ms avg, 0.0 ms total
                         select p1_0.id,p1_0.name,p1_0.price,p1_0.sku from product p1_0 where p1_0.id=?
1.7 ms     0.0 ms      db SELECT customer
1.8 ms     0.1 ms      INTERNAL Transaction.commit
2.2 ms     2.7 ms      CLIENT GET http://localhost:8081/api/books/155 → 200
3.3 ms     1.0 ms        SERVER silk-bookstore GET /api/books/{id} → 200
3.7 ms     0.1 ms          db SELECT books
5.6 ms     3.1 ms      CLIENT GET http://localhost:8081/api/books/87 → 200
6.5 ms     2.0 ms        SERVER silk-bookstore GET /api/books/{id} → 200
7.2 ms     0.1 ms          db SELECT books

Two spaces of indentation mark each level of depth, and the service is named only where it changes from the parent.
Consecutive sibling spans with the same summary and category collapse after the third into one line with `× n`, the average and the total.
A database span that is slow, or the first of a collapsed group, shows its statement on the next line.
An error span shows its exception and the application frames under it, and the trace's log lines follow, oldest first.
`--full` lists every repeated span and keeps the statements whole.
<<trace,trace and traces>> shows a failed trace with its exception, its frames and its log lines.

[#one-finding]
=== One finding

`+GET /api/findings/{id}?since&until&service+` answers one finding of the window, so a person who sees it in the UI can hand exactly it to an agent.
This is what the UI's xref:pages.adoc#copy-as-markdown[Copy as Markdown] copies.
The rules run over the window as for the list, with no `limit` and with acknowledged and resolved findings included, and the answer is the finding with that id and its `rank` among them.
An id the rules do not produce over the window is `404`.

Its text rendering is written by the code that writes the list, so apart from the heading its lines are the list's bytes:

[source]
----
# finding n-plus-one:1d41bc5a9b2c  2026-09-18T12:37:06+09:00 → 12:41:08  (4m 1s, all services, 2456 requests)

| # | severity | state | kind | id | service | title |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | medium | new | n-plus-one | n-plus-one:1d41bc5a9b2c | orders | GET /orders/{id} runs SELECT order_line 6 times per request |

2. n-plus-one:1d41bc5a9b2c — 1 of 1 request repeated it; 6 times; 12.0 ms per request in that statement
   requests 1, affected 1, medianRepeats 6, maxRepeats 6, msPerRequest 12.0
   select * from order_line where order_id = ?
   traces: 4bf92f3577b34da6a3ce929d0e0e4736
----

The heading is the list's with `finding <id>` in place of `findings`, over the same window and service.
The table has the list's columns and the finding's one row, numbered by its rank, and the evidence block under it is the one `findings` prints for that number.
`findings --since=<from> --until=<to> --limit=100` over the same window prints both unchanged, bar the <<suspect-change,suspect-change lines>> it adds under the code frames, which no HTTP answer carries.

`+GET /api/errors/{errorId}+` and `+GET /api/queries/{queryId}+` answer the same way with `format=text`: the heading `# error <errorId>` or `# query <queryId>` over the window, then the `errors` or `queries` table with the group's one row, and for an error the sample's application frames as the list prints them.
The JSON of those two stays the pages' own (xref:api.adoc#query[One query], xref:api.adoc#error[One error group]).

[#trace-diff]
== Trace diff

`trace <a> --diff=<b> [--full]` aligns two span trees and renders them as one text with a gutter, so after a fix you see which span went away and which one got slower without reading two trees.
Over HTTP it is `+GET /api/traces/{a}?diff={b}+`.

[source]
----
# trace diff 4bf92f3577b34da6a3ce929d0e0e4736 → 09e96c4c6db157e690716c2615ffd146  312.4 ms → 41.2 ms  (−271.2 ms, −86.8%)  48 → 12 spans

   a          b          span
=  312.4 ms   41.2 ms    SERVER spring-orders GET /api/orders/{id}/enriched → 200
=  0.5 ms     0.4 ms       INTERNAL OrderRepository.findById
-  38.2 ms    —            db SELECT product  × 42
+  —          2.1 ms       db SELECT product  × 1
=  9.1 ms     8.7 ms       CLIENT GET http://localhost:8081/api/books/155 → 200
----

The alignment works on the lines of the single-trace rendering, minus their timing.
Each span becomes the key `(depth, category, summary with every run of digits replaced by one ?)`, so `/api/books/155` and `/api/books/87` are the same line, and a collapsed group keeps its summary and drops its count.
The two key sequences are then aligned by their longest common subsequence, each side cut at 2,000 lines.
A matched line is `=`, a line only in `b` is `+`, and a line only in `a` is `-`.

The heading carries both ids, both durations, the delta in milliseconds and in percent of `a`, and both span counts.
The columns are the gutter, `a`'s duration, `b`'s duration, then the span line indented by depth as in the single rendering.
A side with no such span prints `—`.
A collapsed group prints `× n` per side on its own line, so a count that changed is two lines, one `-` and one `+`.

Statement, exception and log lines are not diffed.
A matched span shows its statement or its exception when either side has one, as the single rendering would.

`--full` expands collapsed groups on both sides before aligning.
Either id unknown is a `404` naming it over HTTP, and exit code `4` in the CLI.

The JSON is one object per line of the text:

[source,json]
----
{ "a": "<id>", "b": "<id>", "durationMs": { "a": …, "b": … }, "spans": { "a": 48, "b": 12 },
  "lines": [ { "op": "=" | "+" | "-", "depth": 1, "summary": "…", "category": "…",
               "aMs": … | null, "bMs": … | null, "count": { "a": 42, "b": null } | null } ] }
----

[#tail]
== Tail

[source,bash]
----
java -jar spider-sense.jar tail [--kind=slow-request|slow-query|error] [--service=<name>] [--until-traces=<n>] [--timeout=<duration>] [--json]
----

`tail` is the CLI's window on the live event stream, `GET /api/events` (xref:api.adoc#events[Live events]): one line per `tingle` event as it arrives, so an agent that has just sent a request can watch it land instead of sleeping and asking `findings` again.

[source]
----
12:37:28.565  slow-query    spring-orders   SELECT orders  1,532 ms  2519b548daad800090e8f56de6a5a62a
12:37:29.077  error         silk-bookstore  GET /api/books/stats  ArithmeticException: / by zero  09e96c4c6db157e690716c2615ffd146
----

The columns are local time with milliseconds, kind, service, title, detail and trace id, which are the event's own fields in that order.
`--kind` and `--service` each filter on one value, and without either every event is printed.

`--until-traces=<n>` ends with exit `0` once the `stats` events have shown `n` new traces since the command started, `traces` on a `stats` event being the store's count.
`--timeout=<duration>` takes a selector duration such as `30s` or `5m`, and ends with exit `0` when it elapses.
Without either, `tail` runs until it is interrupted.
`--json` prints the event's JSON object per line instead, with `"event": "tingle"` (or `"stats"`) added.

`tail` needs a running Spider Sense, because there is no file to tail.
Nothing at `--url` is a message on stderr and exit `2`.

[#export-import]
== Export and import

`export` writes the window as one JSON document, and `import` reads that document back into a store.
Together they move a session to another machine, attach it to a bug report, or keep it past the retention.

[source,bash]
----
java -jar spider-sense.jar export --since=start --out=session.json.gz
java -jar spider-sense.jar import session.json.gz
----

`export [--since=… --until=… --service=…] [--out=<file>]` writes to stdout, or to the file `--out` names, gzipped when that name ends in `.gz`.
Over HTTP it is `GET /api/export?since&until&service` (or `from` and `to`) without `traceId`, streamed as it is read, with `Content-Disposition: attachment; filename="spider-sense-<from>-<to>.json"`.
With `traceId` the answer is the single-trace export instead (xref:api.adoc#data[Delete and export]).

The document carries every service, span, log record, metric, metric series, metric point, tingle and mark of the window, and the index catalog (`db_table`) of its services:

[source,json]
----
{ "spiderSense": { "version": "0.1.0", "schema": 4, "exportedAt": …, "window": { "from": …, "to": … }, "service": "…" | null },
  "services": [ { "name": "…", "language": "…", "pid": …, "firstSeen": …, "lastSeen": …, "resource": { … } } ],
  "spans": [ { …every column of the span table except id, attributes and events as the objects they are… } ],
  "logs": [ { …every column of log except id… } ],
  "metrics": [ { "name", "type", "unit", "description", "monotonic", "temporality" } ],
  "metricSeries": [ { "id": 7, "service", "name", "attributes": { … } } ],
  "metricPoints": [ { "seriesId": 7, "atMs", "value", "count", "sum", "min", "max", "buckets": { … } | null } ],
  "tingles": [ { …every column except id… } ],
  "marks": [ { "atMs", "name", "service", "note" } ],
  "dbTables": [ { "service", "schemaName", "tableName", "product", "indexes": [ { "name", "unique", "columns": [ … ] } ], "seenMs" } ] }
----

Every key is its column's name in camelCase, so a section is the table it came from and an import binds it straight back: `at_ms` is `atMs`, `start_ms` is `startMs`, `parent_span_id` is `parentSpanId`.
Nothing is derived on the way out or recomputed on the way in: `entry`, `slow`, `queryId` and the rest travel as they were stored, because a document exported from one session must not change meaning under another machine's thresholds.

`dbTables` is cut by service and not by time.
The extension reads a table's indexes once per process, so the row behind the window's statements was usually written before the window began, and every catalog row of the exported services travels, all of them when no `service` is given.
Its `indexes` is the stored array as an array, or the stored text as a string when that text is not JSON.
A `slow-query` or `n-plus-one` finding over the imported session therefore has the xref:findings.adoc#schema[schema block] it had where it was recorded.

`import <file> [--url=… | --db=…]` posts the document to the running Spider Sense, or, when none answers or `--db` names a file, writes into the file in process through the same code the server uses.
Over HTTP it is `POST /api/import` with the document as the body, `Content-Encoding: gzip` accepted, and the answer is `200` with the counts:

[source,json]
----
{ "spans": n, "logs": n, "metricPoints": n, "tingles": n, "marks": n, "dbTables": n, "skippedTraces": n, "window": { "from": …, "to": … } }
----

The command prints one line:

[source]
----
imported 12,345 spans, 456 logs, 7,890 metric points, 12 tingles, 3 marks (2 traces already present) from 2026-09-18T12:37:06+09:00 → 12:41:08
----

Import keeps every timestamp as exported, so set the time range to the answer's `window`, or to `all`, to see the data.
Import is idempotent enough for a file imported twice.

* A trace whose id already has rows in the store is skipped whole, its spans, logs and tingles, and `skippedTraces` counts it.
* Any other log line or tingle is skipped when an identical row is already stored, which is what keeps a line logged outside a span, such as a worker's job log, from being imported again.
A log line is identified by its service, instant, severity, body, logger and ids, and a tingle by its instant, kind, service, title, detail and ids.
Two identical rows in the file stay two rows.
* A metric point is merged on its `(series, at)` key, with the series looked up or created by `(service, name, attributes)`.
* A service row is inserted when the store has none of that name, and otherwise only widens its first and last sighting, keeping the stored process id, language and resource.
The process id is the one the writer compares to insert a `start` mark, so an imported one would move `since=start` to the moment of the import.
* A mark is skipped when one with the same name and instant exists, and a `start` mark is never imported: it would claim a run of an application that is not running here and become the newest start of its service.
* A catalog row is merged on its key `(service, schema_name, table_name)` as the writer merges it (xref:storage.adoc#writer[How it is written]), so the table the file describes replaces the row the store had for it.

A document whose `schema` is not this version's is a `400` naming both versions.
A document that is not JSON, or whose rows are not the shapes `export` writes, is a `400` naming what did not decode, and nothing of it is written.
Acknowledgements and resolutions are not exported, because they are the reader's rather than the session's.

[#sql]
== SQL

[source,bash]
----
java -jar spider-sense.jar sql "SELECT endpoint, COUNT(*) FROM span WHERE entry GROUP BY endpoint"
----

`sql "<statement>" [--limit=200]` runs one read-only statement over the schema, for a question no other command answers.
It is the escape hatch.
Findings, compare and check answer what Spider Sense knows to look for, and everything else it holds is already documented by xref:storage.adoc#schema[the schema].
Reach for it last: `findings`, `endpoints`, `queries`, `errors`, `compare` and `check` are the same data with the thresholds, the ranking and the rendering already applied, and they stay correct when the schema changes.

The index catalog the extension reads is there too, as `db_table`.
`SELECT table_name, indexes FROM db_table WHERE service = 'servlet-warehouse'` lists every table a slow statement of that service has touched, with its indexes as JSON.

Over HTTP it is `POST /api/sql` with `{ "sql": "SELECT …", "limit": 200 }`.
`format=text` as a query parameter, or an `Accept` whose first type is `text/markdown` or `text/plain`, selects the Markdown rendering, and the JSON is otherwise:

[source,json]
----
{
  "columns": ["ENDPOINT", "STATEMENTS"],
  "rows": [ ["GET /orders/{id}", 42], ["GET /orders", 7] ],
  "rowCount": 2,
  "truncated": false,
  "elapsedMs": 3
}
----

A value is a JSON number, string, boolean or null, as the store holds it.
Every instant in the schema is epoch milliseconds and stays a number, and an H2 `TIMESTAMP` a statement computes itself is an ISO string.

The answer is a heading and a table:

[source]
----
# sql  2 rows

| ENDPOINT | STATEMENTS |
| --- | --- |
| GET /orders/{id} | 42 |
| GET /orders | 7 |
----

The column headers are H2's own labels, which upper-case an unquoted name (`SERVICE`, `SPANS`), so alias a column when the heading matters.
At most 200 rows come back unless `--limit=<n>` says otherwise, and the cap is 5000; a limit below 1 is a `400`.
One row more than the limit is fetched, so `truncated` reports whether the cap cut the answer off rather than guessing at it.
The heading carries ` (truncated at 200)` when the cap cut the answer off, and a truncated answer is a sample rather than a total.
`--json` prints `columns`, `rows`, `rowCount`, `truncated` and `elapsedMs` instead of the table.

The <<text-rendering,conventions>> hold here too.
Nothing in the body depends on when it was rendered, so `elapsedMs` is in the JSON only.
A cell is cut at 200 characters with `…` unless `--full` (`full=true`) is given, a `|` in a cell is escaped, and its newlines collapse to spaces.
Numbers are printed as the store holds them, without a thousands separator, because a value passed back into the next statement has to survive the round trip.
A SQL `NULL` is `—`.

[#read-only]
=== Read-only, in three layers

Each layer catches what the one before it cannot, and the second is the one that holds.

. *A statement allowlist.*
After the leading whitespace and the `--` and `/* */` comments are stripped, the first keyword must be `SELECT`, `WITH`, `TABLE`, `VALUES`, `EXPLAIN` or `SHOW`, and there must be one statement: a `;` followed by anything but whitespace is refused.
String literals and comments make this a scanner over SQL text rather than a parser, which is exactly why it is not the layer that is trusted.
. *A user with `SELECT` and nothing else.*
The schema creates `spider_sense_reader`, idempotently, on every open by a server of this version, and grants it `SELECT` on schema `PUBLIC` (xref:storage.adoc#reader[The read-only user]).
The statement runs on a connection opened as that user, with the same JDBC URL.
H2 itself therefore refuses `INSERT`, `UPDATE`, `DELETE`, `DROP` and `ALTER` with "Not enough rights for object", and the administrator-only functions `FILE_WRITE`, `CSVWRITE`, `FILE_READ`, `LINK_SCHEMA` and `RUNSCRIPT` with "Admin rights are required for this operation", whatever the layer above thought it read.
. *The limits of the connection.*
`setMaxRows(limit + 1)`, a query timeout of 10 seconds, `setReadOnly(true)`, autocommit off, and a `rollback()` whatever happens.

Only a server creates the reader user, when it opens the database.
The direct-file path opens the reader connection the same way, and a database an older Spider Sense created has no reader user in it yet.
`sql` then reports `the database has no read-only user yet; start an application or the standalone server with this version first` on stderr and exits `2`.

A statement that is not allowed is a `400` with `{ "error": "…" }` naming the reason, and a statement H2 refuses or cannot parse is a `400` carrying H2's own message.
In the text rendering, and so in the CLI, an error is that message on one line, because an agent that asked for Markdown should not have to parse a JSON object it did not expect.

[#sql-window]
=== Bounding the window

There is no `--since` here, because the window is a predicate you write.
Every instant in the schema is epoch milliseconds in a `BIGINT`, and every duration is nanoseconds, so arithmetic on times is plain integer arithmetic.
Two idioms cover almost everything:

[source,sql]
----
-- the last 15 minutes of data, whenever the data ends
WHERE s.start_ms >= (SELECT MAX(start_ms) FROM span) - 15 * 60 * 1000

-- since the mark you set before the change
WHERE s.start_ms >= (SELECT MAX(at_ms) FROM mark WHERE name = 'before')
----

`(SELECT MAX(at_ms) FROM mark WHERE name = 'start')` is the last restart.
Without a predicate on `start_ms` or `at_ms` the query reads the whole retention, which is up to 24 hours of everything.

The three flags on `span` are the shortcuts worth remembering: `entry` counts requests, `category = 'db'` counts statements, and `error` counts failures.
xref:storage.adoc#schema[The schema] has every table and column.

[#sql-examples]
=== Worked queries

The endpoints that issue the most distinct statements, a ranking `findings` cannot make.
An endpoint may run few statements often or many statements once, and the second is a design question rather than an N+1.

[source,sql]
----
SELECT e.endpoint,
       COUNT(DISTINCT d.query_id) AS statements,
       COUNT(d.id)                AS db_calls,
       COUNT(DISTINCT e.id)       AS requests
FROM span e
JOIN span d ON d.trace_id = e.trace_id AND d.service = e.service AND d.category = 'db'
WHERE e.entry
  AND e.start_ms >= (SELECT MAX(start_ms) FROM span) - 15 * 60 * 1000
GROUP BY e.endpoint
ORDER BY statements DESC, db_calls DESC
----

The p95 per minute for one route.
Findings give one p95 over the window, and this says whether it was the whole window or one bad minute.

[source,sql]
----
SELECT s.start_ms / 60000 * 60000 AS minute_ms,
       COUNT(*) AS requests,
       ROUND(PERCENTILE_DISC(0.95) WITHIN GROUP (ORDER BY s.duration_ns) / 1000000.0, 1) AS p95_ms,
       ROUND(MAX(s.duration_ns) / 1000000.0, 1) AS max_ms
FROM span s
WHERE s.entry AND s.endpoint = 'GET /orders/{id}'
GROUP BY s.start_ms / 60000 * 60000
ORDER BY minute_ms
----

The statements of one trace, in order.
`trace <id>` collapses repeated siblings, and this lists every one of them with its offset, which is what to read when the repeats are not identical.

[source,sql]
----
SELECT s.start_ns - (SELECT MIN(start_ns) FROM span WHERE trace_id = s.trace_id) AS offset_ns,
       ROUND(s.duration_ns / 1000000.0, 1) AS ms,
       s.service, s.db_operation, s.db_table, s.db_statement
FROM span s
WHERE s.trace_id = '4bf92f3577b34da6a3ce929d0e0e4736' AND s.category = 'db'
ORDER BY s.start_ns

Errors per endpoint per hour.
Findings rank error groups over one window, and this says whether a group is growing.

[source,sql]
----
SELECT s.start_ms / 3600000 * 3600000 AS hour_ms,
       s.service, s.endpoint,
       COUNT(*) AS requests,
       SUM(CASE WHEN s.error THEN 1 ELSE 0 END) AS errors
FROM span s
WHERE s.entry
GROUP BY s.start_ms / 3600000 * 3600000, s.service, s.endpoint
HAVING SUM(CASE WHEN s.error THEN 1 ELSE 0 END) > 0
ORDER BY hour_ms DESC, errors DESC
----

The pools' worst pending value per five minutes.
The `pool-exhausted` finding names the single worst point, and this is the shape of the pressure over time.

[source,sql]
----
SELECT p.at_ms / 300000 * 300000 AS five_minutes_ms,
       ms.service, ms.attributes AS pool,
       MAX(p.value) AS pending_max
FROM metric_point p
JOIN metric_series ms ON ms.id = p.series_id
WHERE ms.name IN ('db.client.connections.pending_requests', 'db.client.connection.pending_requests')
GROUP BY p.at_ms / 300000 * 300000, ms.service, ms.attributes
ORDER BY five_minutes_ms DESC
----

The requests that ran the most statements.
The N+1 rule fires at 5 repeats of one statement, and this finds a request that ran 40 different ones, which is not an N+1 and is still worth seeing.

[source,sql]
----
SELECT e.endpoint, e.trace_id, COUNT(*) AS db_calls,
       ROUND(SUM(d.duration_ns) / 1000000.0, 1) AS db_ms
FROM span e
JOIN span d ON d.trace_id = e.trace_id AND d.category = 'db'
WHERE e.entry
GROUP BY e.endpoint, e.trace_id
HAVING COUNT(*) >= 10
ORDER BY db_calls DESC
----

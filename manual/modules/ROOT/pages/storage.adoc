= Storage
:navtitle: Storage

Spider Sense keeps what it collects in an H2 file database under the user's home directory.
The UI therefore still answers after the monitored application has stopped, and every Spider Sense process on the machine, embedded or standalone, sees the same data.

[#where]
== Where

The default JDBC URL is `jdbc:h2:~/db/spider-sense/sense;AUTO_SERVER=TRUE`, which is the file `~/db/spider-sense/sense.mv.db`.
`sense.trace.db` appears beside it when H2 logs a problem.
`spidersense.db` overrides the URL with a path (`~/db/other/sense`) or a full `jdbc:h2:` URL.

`AUTO_SERVER=TRUE` lets embedded and standalone Spider Sense processes share the file without any setup:

* The first process to open the file becomes its server.
A second process that opens the same URL connects to the first over a local TCP port, transparently.
Two applications each embedding Spider Sense, plus a standalone `java -jar spider-sense.jar` opened to look at both, all share one database at once.
* When the process holding the file exits, the next opener takes over.
Stop the application, run `java -jar spider-sense.jar`, and the traces of the session that just ended are on screen.

The H2 driver runs inside the `SenseClassLoader`, which the OpenTelemetry agent is told to leave alone.
The application's traces therefore never contain Spider Sense's own SQL.
An application that uses H2 itself loads its own copy of the driver in its own class loader, and the two copies never meet.

[#schema]
== What is stored

There is one row per span, log record, metric point, tingle and mark (a named moment, see xref:marks-and-compare.adoc#marks[Marks]), plus a per-trace summary row that the writer maintains.
The lists and aggregations the API serves are therefore SQL over indexed columns rather than a scan of blobs.
Attributes and events are kept as JSON text in the same row.
The columns beside them hold the values the queries need, extracted once at ingest.

[source,sql]
----
CREATE TABLE IF NOT EXISTS service (
    name         VARCHAR(255) PRIMARY KEY,
    language     VARCHAR(64),
    pid          BIGINT,
    first_seen   BIGINT NOT NULL,          -- epoch ms
    last_seen    BIGINT NOT NULL,
    resource     VARCHAR(65535) NOT NULL   -- JSON object of the resource attributes
);

CREATE TABLE IF NOT EXISTS span (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    trace_id       CHAR(32) NOT NULL,
    span_id        CHAR(16) NOT NULL,
    parent_span_id CHAR(16),
    service        VARCHAR(255) NOT NULL,
    name           VARCHAR(1024) NOT NULL,
    kind           VARCHAR(8) NOT NULL,      -- SERVER CLIENT INTERNAL PRODUCER CONSUMER
    start_ms       BIGINT NOT NULL,
    start_ns       BIGINT NOT NULL,
    duration_ns    BIGINT NOT NULL,
    status         VARCHAR(5) NOT NULL,      -- UNSET OK ERROR
    status_message VARCHAR(4096),
    entry          BOOLEAN NOT NULL,         -- SERVER/CONSUMER, or a non-db root CLIENT/PRODUCER, unless the endpoint is ignored (Endpoint identity)
    error          BOOLEAN NOT NULL,
    slow           BOOLEAN NOT NULL,         -- entry over slow.request.ms, or db over slow.query.ms
    category       VARCHAR(10) NOT NULL,     -- http db messaging rpc internal
    endpoint       VARCHAR(1024),            -- entry spans: the endpoint name (see Endpoint identity)
    endpoint_id    CHAR(12),
    http_method    VARCHAR(16),
    http_route     VARCHAR(1024),
    http_status    INT,
    db_system      VARCHAR(64),
    db_statement   VARCHAR(4096),            -- cut at 2000 characters
    db_namespace   VARCHAR(255),
    db_operation   VARCHAR(64),
    db_table       VARCHAR(255),
    query_id       CHAR(12),
    error_type     VARCHAR(512),
    error_message  VARCHAR(4096),            -- as received
    error_id       CHAR(12),                 -- hash over the root cause and its frame, or the normalised message
    scope          VARCHAR(255),
    attributes     VARCHAR(65535) NOT NULL,  -- JSON object; the longest string values cut to fit, ending in …
    events         VARCHAR(65535) NOT NULL   -- JSON array; cut the same way
);
CREATE INDEX IF NOT EXISTS span_start   ON span (start_ms);
CREATE INDEX IF NOT EXISTS span_trace   ON span (trace_id);
CREATE INDEX IF NOT EXISTS span_service ON span (service, start_ms);
CREATE INDEX IF NOT EXISTS span_endpoint ON span (endpoint_id, start_ms);
CREATE INDEX IF NOT EXISTS span_query   ON span (query_id, start_ms);
CREATE INDEX IF NOT EXISTS span_error   ON span (error_id, start_ms);

CREATE TABLE IF NOT EXISTS trace (
    trace_id     CHAR(32) PRIMARY KEY,
    start_ms     BIGINT NOT NULL,
    end_ms       BIGINT NOT NULL,
    duration_ns  BIGINT NOT NULL,          -- last span end minus first span start
    root_span_id CHAR(16),
    root_name    VARCHAR(1024) NOT NULL,
    root_service VARCHAR(255) NOT NULL,
    root_kind    VARCHAR(8) NOT NULL,
    services     VARCHAR(4096) NOT NULL,     -- JSON array
    span_count   INT NOT NULL,
    error_count  INT NOT NULL,
    db_count     INT NOT NULL,
    http_status  INT,
    slow         BOOLEAN NOT NULL,
    error        BOOLEAN NOT NULL
);
CREATE INDEX IF NOT EXISTS trace_start   ON trace (start_ms);
CREATE INDEX IF NOT EXISTS trace_service ON trace (root_service, start_ms);

CREATE TABLE IF NOT EXISTS log (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    at_ms           BIGINT NOT NULL,
    service         VARCHAR(255) NOT NULL,
    severity_number INT NOT NULL,
    severity        VARCHAR(8) NOT NULL,
    body            VARCHAR(65535) NOT NULL,
    logger          VARCHAR(512),
    trace_id        CHAR(32),
    span_id         CHAR(16),
    attributes      VARCHAR(65535) NOT NULL
);
CREATE INDEX IF NOT EXISTS log_at      ON log (at_ms);
CREATE INDEX IF NOT EXISTS log_trace   ON log (trace_id);
CREATE INDEX IF NOT EXISTS log_service ON log (service, at_ms);

CREATE TABLE IF NOT EXISTS metric (
    service     VARCHAR(255) NOT NULL,
    name        VARCHAR(255) NOT NULL,
    type        VARCHAR(12) NOT NULL,        -- gauge sum histogram
    unit        VARCHAR(64),
    description VARCHAR(1024),
    monotonic   BOOLEAN NOT NULL,
    temporality VARCHAR(12),                 -- cumulative delta
    PRIMARY KEY (service, name)
);

CREATE TABLE IF NOT EXISTS metric_series (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    service    VARCHAR(255) NOT NULL,
    name       VARCHAR(255) NOT NULL,
    attr_hash  CHAR(12) NOT NULL,
    attributes VARCHAR(4096) NOT NULL,       -- JSON object, keys sorted
    CONSTRAINT metric_series_key UNIQUE (service, name, attr_hash)
);

CREATE TABLE IF NOT EXISTS metric_point (
    series_id BIGINT NOT NULL,
    at_ms     BIGINT NOT NULL,
    value     DOUBLE,                        -- gauge/sum value, histogram mean
    count     BIGINT,                        -- histogram
    sum       DOUBLE,
    min       DOUBLE,                        -- NULL when the sender did not report it (optional in OTLP)
    max       DOUBLE,
    buckets   VARCHAR(8192),                 -- JSON {"bounds":[...],"counts":[...]}
    PRIMARY KEY (series_id, at_ms)
);

CREATE TABLE IF NOT EXISTS tingle (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    at_ms       BIGINT NOT NULL,
    kind        VARCHAR(16) NOT NULL,        -- slow-request slow-query error
    service     VARCHAR(255) NOT NULL,
    title       VARCHAR(1024) NOT NULL,
    detail      VARCHAR(4096) NOT NULL,
    trace_id    CHAR(32),
    span_id     CHAR(16),
    duration_ms DOUBLE
);
CREATE INDEX IF NOT EXISTS tingle_at ON tingle (at_ms);

CREATE TABLE IF NOT EXISTS mark (
    id       BIGINT AUTO_INCREMENT PRIMARY KEY,
    at_ms    BIGINT NOT NULL,
    name     VARCHAR(64) NOT NULL,         -- [A-Za-z0-9._-]; "start" is written by the writer
    service  VARCHAR(255),
    note     VARCHAR(1024)
);
CREATE INDEX IF NOT EXISTS mark_at ON mark (at_ms);

CREATE TABLE IF NOT EXISTS ack (
    finding_id VARCHAR(64) PRIMARY KEY,     -- the finding id, kind + ':' + 12 hex (Findings)
    at_ms      BIGINT NOT NULL,
    note       VARCHAR(1024),
    resolved   BOOLEAN NOT NULL DEFAULT FALSE  -- a resolution rather than an acknowledgement
);

CREATE TABLE IF NOT EXISTS db_table (
    service     VARCHAR(255) NOT NULL,
    schema_name VARCHAR(255) NOT NULL,       -- '' when the database reports none
    table_name  VARCHAR(255) NOT NULL,       -- as the database reports it: ITEMS on H2, items on PostgreSQL
    product     VARCHAR(64),                 -- DatabaseMetaData.getDatabaseProductName()
    indexes     VARCHAR(65535) NOT NULL,     -- JSON array [{"name":…,"unique":…,"columns":[…]}], columns in key order
    seen_ms     BIGINT NOT NULL,
    PRIMARY KEY (service, schema_name, table_name)
);

CREATE TABLE IF NOT EXISTS meta (
    key   VARCHAR(64) PRIMARY KEY,
    value VARCHAR(4096) NOT NULL             -- schema_version, created_at
);
----

The schema is created with `IF NOT EXISTS` at startup.
The stored `meta.schema_version` is read before any table is created.
A database of another version therefore has its tables dropped before this version's are created, since an index of this version may be on a column an older table lacks.
The CLI, which refuses another version, leaves such a database exactly as it found it.
It also refuses a database without `meta`: one that holds tables is one Spider Sense never wrote, such as the application's own named by a mistaken `--db`, and an empty one, such as the one behind a `jdbc:h2:mem:` URL, gets no tables from the CLI.
`meta.schema_version` is `8`, the version that keyed `metric` by service as well as name.
Version 7 moved the error group key to the root cause and its frame, version 6 added the `resolved` column of `ack`, version 5 added `db_table`, version 4 added `ack`, and version 3 added `mark`.
A version that changes a table or the meaning of a stored id drops and recreates every table, because the data is a cache of a development session and not a record.
Version 7 changed every `error_id`, and so the id of every `error` finding.
Acknowledgements and resolutions recorded before the upgrade are therefore lost with the rest of the tables, rather than kept as rows nothing can reach.
An `ack` row is an acknowledged finding (xref:findings.adoc#acknowledgements[Acknowledgements]), or, with `resolved` true, a resolved one (xref:findings.adoc#resolutions[Resolutions]).
The two share a table because a finding has one decision recorded at a time, and the newer one replaces the older through the same `MERGE INTO ack … KEY (finding_id)`.
The retention sweeper does not delete an `ack` row by age, since a known finding stays known and a fixed one stays fixed.
`DELETE /api/data` removes it with everything else.
A `db_table` row is the index catalog of one table of one service, as the extension read it through JDBC metadata (xref:design.adoc#extension[The extension]).
It arrives as a log record whose attributes are `spidersense.schema.table`, `spidersense.schema.schema`, `spidersense.schema.product` and `spidersense.schema.indexes`.
The decoder turns that record into a catalog row instead of a log line.
The row is merged on its key (`MERGE INTO db_table … KEY (service, schema_name, table_name)`), so a table looked up again after a restart replaces its row.
The `indexes` text is stored as received, and the findings read it back (xref:findings.adoc#schema[The schema block] in Findings).
`entry` is decided once, when the row is written, so rows written by an older Spider Sense keep the flag they were written with.
A root `INTERNAL` or database span from before the `entry` rule narrowed still counts as a request until the retention sweeper removes it.

The endpoint name and the ignored endpoints that the `span` comments name are defined in xref:design.adoc#endpoint-identity[Endpoint identity].
The finding id in the `ack` table is the one xref:findings.adoc[Findings] defines.

[#reader]
== The read-only user

Beside the tables, the schema creates one H2 user, `spider_sense_reader`, with `CREATE USER IF NOT EXISTS` and a constant password, and grants it `SELECT` on schema `PUBLIC`.
`POST /api/sql` and the CLI's xref:cli.adoc#sql[`sql`] run their statements as this user.
Because the user has `SELECT` and nothing else, H2 itself refuses every write, every piece of DDL and the administrator-only functions (`FILE_WRITE`, `CSVWRITE`, `FILE_READ`, `LINK_SCHEMA`, `RUNSCRIPT`) to any statement that gets that far.
The grant is on the schema rather than on the tables, so it covers a table a later version adds without a `schema_version` bump.
Creating the user is idempotent on every open.
Only a server creates the user when it opens the database, and the CLI never does.
Through `AUTO_SERVER=TRUE` the CLI may have joined the database of an older Spider Sense, and adding a user to it is as much a change to somebody else's database as recreating its tables would be.
The reader connects with the same JDBC URL minus the settings a non-administrator may not apply, keeping only `AUTO_SERVER` and `NON_KEYWORDS`.
H2 turns most of those settings into a `SET` at connect time.
`DB_CLOSE_DELAY`, which the in-memory fallback sets, is one an ordinary user is refused.

[#writer]
== How it is written

Ingest never touches the database on the request thread.
The OTLP handler decodes the request into records and hands them to a `Writer`.
The `Writer` is a bounded queue of 10,000 batches drained by one daemon thread.
When the queue is full, the oldest batch is dropped and `/api/status.storage.droppedBatches` increments.
The thread flushes every 200 ms, or as soon as 500 records are waiting, in one transaction per flush with JDBC batch inserts.
Every text value is cut to its column before it is bound: a service or metric name at 255 characters as it is decoded, so every table holds the same name, and a trace's `services` by leaving out the names past its width.
A histogram point whose buckets do not fit their column keeps its count, sum, min and max and is stored without buckets.
A double attribute that JSON has no number for, `NaN` or an infinity, is stored as the string `"NaN"`, `"Infinity"` or `"-Infinity"`.
When a flush still fails, each of its batches is written again in a transaction of its own, so a row the database refuses costs only the export that carried it.
A failed flush is rolled back whole before that, whatever failed, a stack overflow on an attribute nested thousands of levels deep included, so no batch is stored twice.
The catalog rows of a flush are merged in the same transaction.
After each flush the writer recomputes the `trace` rows of the trace ids the flush touched (`MERGE INTO trace ... SELECT ... FROM span WHERE trace_id IN (...) GROUP BY trace_id`), because a trace's spans arrive in several exports and from several services.
It locks those rows first, by merging a placeholder in trace id order, and only then reads their spans.
The spans are read 500 trace ids at a time, because H2's cost for one `IN` list grows with the square of its length, and a flush after a burst or an import touches tens of thousands of traces.
Another process sharing the file may be flushing the other half of the same trace; the lock makes the second writer wait for the first one's commit and read every span, where it would otherwise overwrite the row with its own half.
It then publishes the flush's tingles and counts to the SSE stream.
The `service` row is merged on every flush that carries the service.
When the sighting carries a `process.pid` that differs from the stored one, or the row is new, the writer also inserts a `mark` named `start` for that service with the note `pid <pid>`.
`since=start` resolves to that mark.
A JVM shutdown hook flushes what is queued, and then closes the database.
H2 closes a file database from an exit hook of its own, and the JVM runs its hooks concurrently in no set order, so H2 may close the pool's connections under that flush.
`DB_CLOSE_ON_EXIT=FALSE`, which turns H2's hook off, is refused beside `AUTO_SERVER=TRUE`, so the flush survives the race instead of avoiding it.
It writes through a connection of its own outside the pool.
Opened while H2 is closing the file, that connection waits for the close to finish and opens the file again, and a write that H2 closed under it is tried again the same way.
Once the rows are in, the flush shuts down the engine this process holds, so the file is written and closed before the JVM halts, whichever hook ran first.
After the flush at exit has begun, the writer's thread writes nothing more, since writing through the pool after H2 closed the file would open it again behind that flush.

Metric points are written on the same path.
A `metric` row describes one service's instrument, so two services that export one name as different instruments, one a `CUMULATIVE` sum and the other a `DELTA` sum, keep a row each, and each service's points are read by its own row.
A series row is looked up by `(service, name, attr_hash)` through a small in-memory cache of ids.
The sweeper and `DELETE /api/data`, in this process or in any other sharing the file, delete series rows behind that cache.
Each flush that carries metric points therefore checks, in one `SELECT`, that the cached ids of its series still have a row, and looks up or creates again a series whose row is gone.
That check locks the series rows (`FOR UPDATE`), and the sweep of series with no point left locks its candidates and checks again before it deletes them, so a sweep running while a flush adds the first points of a series waits for that flush and keeps the series.

[#ingest-cap]
=== The ingest cap

`spidersense.ingest.max-spans-per-second` protects the file from a load test.
It is unset by default.
The receiver counts the spans it has accepted in the current wall-clock second.
Once the count is over the cap, the first span of a trace it has not decided yet is dropped, and a span of a trace already accepted is kept.
A trace is decided once: every later span of a dropped trace is dropped too, even in a later second when the count is back under the cap, and does not count toward that second.
The decisions are kept for the last 10,000 accepted and the last 10,000 dropped trace ids, two bounded, insertion-ordered sets, so a burst of dropped traces never pushes out an accepted one.
A span of a trace that has fallen out of both sets is decided afresh.
Every stored trace therefore stays complete, and the dropped ones are whole traces, as long as a trace's spans arrive while its decision is still kept.
Logs and metric points are never dropped.
The dropped spans are counted in `/api/status.storage.droppedSpans` and carried on the SSE `stats` event as `droppedSpans`.
The UI shows the number in the sidebar foot while it grows (xref:ui.adoc[Layout and Controls]).

[#reads]
== How it is read

Every API answer is one or a few SQL statements over the window:

* Lists (`trace`, `log`, `tingle`, scatter points): `WHERE start_ms BETWEEN ? AND ?` with the filters as further predicates, then `ORDER BY start_ms DESC LIMIT ?`.
The trace list breaks a tie inside one millisecond by `trace_id`, and the log list by `id`, so the `before` and `beforeId` cursor of xref:api.adoc#ordering[Ordering and sorting] pages without a gap.
* Aggregations (services, endpoints, queries, errors): `GROUP BY` over `span` with `COUNT(*)`, `SUM(...)`, `MAX(...)` and `PERCENTILE_DISC(0.5|0.95|0.99) WITHIN GROUP (ORDER BY duration_ns)`, which H2 2.x supports.
The response-time histogram is four more `SUM(CASE WHEN NOT error AND duration_ns <= :bound ...)` columns in the same statements, with the bounds derived from `slow.request.ms`.
Apdex is arithmetic over them in Java.
* Time series: `GROUP BY start_ms / :bucket` for counts, errors, histogram buckets and percentiles per bucket.
* The service map: `service → service` edges are one self-join, `span c JOIN span p ON p.trace_id = c.trace_id AND p.span_id = c.parent_span_id WHERE c.entry AND p.service <> c.service`, grouped by the two services.
The external targets reuse the dependency scan, which is the outbound spans of the window capped at 20,000 rows, minus the spans that self-join found.
* A trace: `SELECT ... FROM span WHERE trace_id = ? ORDER BY start_ns, span_id`, plus its logs.
The span id breaks a tie, so two readings of one trace list its spans alike.
* Findings (xref:findings.adoc[Findings]): `n-plus-one` is `GROUP BY trace_id, query_id HAVING COUNT(*) >= 5` over the database spans of the window, attributed to the entry span by the same parent-chain walk the query callers use.
Every such pair of the window is read, with no limit, so a finding's `affected` counts the same requests its `requests` does.
`dbCallsPerRequest` and `dbMsPerRequest` of an endpoint join the endpoint's entry spans with the database spans of the same trace and service.
`slow-job` is the same aggregation over `span WHERE parent_span_id IS NULL AND kind = 'INTERNAL'` grouped by `(service, name)`, with the database work joined the same way.
Only the endpoints and jobs that crossed the threshold are joined, since only they become findings; a job's runs are read by its service's `(service, start_ms)` index, and so is its newest run, whose attributes give the code frames.
`slow-query` and `slow-job` put their threshold in the statement, `HAVING PERCENTILE_DISC(0.95) WITHIN GROUP (ORDER BY duration_ns) > :thresholdNs`, and read every group that passes it rather than the top of a list.
The other kinds are the endpoint, query and error aggregations above, filtered by the thresholds.
A scan of the window that several rules need is made once per answer and handed to each of them.
The parent-chain walk is one: the query callers, the error endpoints, `n-plus-one`, `n-plus-one-http`, `slow-external` and `log-error` all read the same one.
The outbound HTTP spans are the other: `n-plus-one-http` and `slow-external` read the same rows.
Every outbound HTTP span of the window is read, with no limit, because the call's target and name live in its attributes and a finding counts every call and every request of the window.
A row is held as the names it is grouped by and its measures, without its attributes, which are read again by span id for the one call a finding takes its code from.
For one service the walk reads only the traces that have a span of that service in the window, which is where every entry span its spans can reach lies.
The query and error lists read it the same way, so a finding's callers and endpoints are the list's.
* The traces that contain a group (a finding's evidence and sample, the slowest and newest traces of the endpoint, query and error pages): `SELECT * FROM trace t WHERE t.start_ms BETWEEN ? AND ? AND t.trace_id IN (SELECT s.trace_id FROM span s WHERE s.<group> = ? AND s.start_ms BETWEEN ? AND ?)`.
The matching span starts in the window too, so the subquery is a range of the group's `(…, start_ms)` index.
It costs the window's share of the group, never its whole history.
* The xref:findings.adoc#schema[schema block] of a query group: `SELECT schema_name, table_name, indexes FROM db_table WHERE service = ?`, read once per answer and matched against each statement's tables in Java, case-insensitively.
* A time selector that names a mark: `SELECT at_ms FROM mark WHERE name = ? [AND service = ?] ORDER BY at_ms DESC LIMIT 1`.
* The acknowledgements and resolutions of a page of findings: `SELECT * FROM ack WHERE finding_id IN (…)`, one statement for the page.
A finding's xref:findings.adoc#state[state] reads the two newest `start` marks of its service with `SELECT at_ms FROM mark WHERE name = 'start' AND service = ? AND at_ms <= ? ORDER BY at_ms DESC LIMIT 2`.
It runs the rules of the page's kinds again over the run between those two marks, for ids alone, and keeps what they found in memory for as long as the server runs.
* Free-text search (`q`): `+LOWER(name) LIKE ? ESCAPE '\' OR LOWER(attributes) LIKE ? ESCAPE '\'+` over the spans of the window, and `+LOWER(body) LIKE ? ESCAPE '\' OR LOWER(logger) LIKE ? ESCAPE '\' OR LOWER(attributes) LIKE ? ESCAPE '\'+` over its logs.
The pattern is the lower-cased text with its `%`, `_` and `\` escaped, between two `%`.
A scan of the window is acceptable at local-development volumes.
* JVM and metrics: `metric_point` joined with `metric_series`, resampled in Java where the API asks for it.

Connections come from H2's `JdbcConnectionPool`, at most 8, and the writer holds one of its own.
The process that opens the file sizes H2's page cache to its own heap: a sixteenth of the maximum heap, never below H2's 16 MiB and never above 256 MiB.
Every scan of a window reads the window's pages, and a cache smaller than them reads each page from the file again on every scan; findings makes several.
The cache lives in the heap of the process that owns the engine, which is the monitored application in embedded mode, so it is a share of that heap rather than a fixed size.
A process that joined another one's engine through `AUTO_SERVER` leaves the size alone, and so does a JDBC URL that names `CACHE_SIZE` itself.
Reads are plain JDBC through one small helper, `Sql.query(sql, params, rowMapper)`.
There is no ORM and no spring-jdbc, so the nested server jar carries only H2 beyond what it already has.

The xref:cli.adoc[CLI] reads the same way when no server answers.
It opens the same URL, so it joins a running auto-server, or opens the file itself for the length of the command when none is running.
It runs the same `Queries` without a writer or a sweeper.
Its open refuses a missing file, and refuses another `schema_version` instead of dropping the tables, since the database it joined may belong to an older server that is still writing to it.
The commands that write are `mark`, `ack` and `unack`, `resolve` and `unresolve`, and `import`, and they write through the same connection with plain statements.
`import` alone inserts spans, and it does so through the `Writer`'s own insert and `trace` merge, so an imported trace is stored exactly as a received one (xref:cli.adoc#export-import[Export and import]).

[#retention]
== Retention

`spidersense.retention.hours` defaults to `24`.
A daemon sweeper runs a minute after start and every five minutes after that, deleting with `DELETE FROM span|trace|log|metric_point|tingle|mark|db_table WHERE <time> < now - retention`, then `metric_series` rows with no points.
A catalog row goes by its `seen_ms`, because a catalog older than the retention describes a run no window can show any more.
Each service's newest `start` mark is spared: the writer inserts one only when the process id changes, so a service that has run for longer than the retention would otherwise have none, and `since=start` would fail for it.
`DELETE /api/data` runs the same deletes without the time bound, and empties `ack`, acknowledgements and resolutions alike.
At 24 hours of a few requests per second the file stays in the low hundreds of megabytes.
H2 reclaims space on the next compaction, when the database closes.

Retention is by time, with one row cap as a guard: `spidersense.retention.spans`, default 1,000,000, and `0` for none.
After the time sweep, while `SELECT COUNT(*) FROM span` is above the cap, the sweeper takes the oldest hour of data (`MIN(start_ms)` of `span`, plus one hour) and deletes every row of `span`, `trace`, `log`, `metric_point` and `tingle` before that instant.
Marks and catalog rows are included only when they are older than the retention, as before.
The sweeper proceeds one hour at a time, so a cap crossed by a little costs a little.
The cap is by rows rather than by file size because an H2 file does not shrink when rows go.
A size read after a delete would say the same number and ask for the next hour, until nothing was left.
`/api/status.retention` reports both limits, as `{ "hours": 24, "spans": 1000000 }`.

[#failure]
== Failure

If the database cannot be opened, because the file is corrupt or a permission is missing, the server logs one line and falls back to `jdbc:h2:mem:spidersense-<pid>` so the UI still works for the session.
It marks `/api/status.storage.fallback` as `true` with the reason, which is H2's own message.
Only a race with another process opening the same file at the same moment is retried, for up to 15 seconds; any other failure falls back at once, since the open runs on the monitored application's `premain` thread.
Nothing in this path throws out of `premain`.

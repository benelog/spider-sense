= The Three Modes
:navtitle: The Three Modes

One jar runs three ways: as an agent that also hosts the UI, as an agent that forwards to a Spider Sense elsewhere, and as a collector and UI on their own.
The command line is a fourth way in, and it starts no server at all.

Spider Sense is a `-javaagent`, so it has to be on the JVM's command line when the application starts.
An application that is already running cannot be brought under it, and there is no supported way to attach later.
Restart the application with `-javaagent` on its command line.

The examples below assume the jar's absolute path is in `$SENSE`, as xref:install.adoc#from-source[Installation] sets it.

[cols="1,2,2",options="header"]
|===
| Mode | Command | When

| Agent
| `java -javaagent:"$SENSE" -jar app.jar`
| One application. The collector and the UI run inside its JVM on port 4000.

| Agent, forwarding
| `java -javaagent:"$SENSE" -Dspidersense.collector=http://127.0.0.1:4000 -jar app.jar`
| Several applications sharing one Spider Sense, or an application that must not host a web server.

| Standalone
| `java -jar "$SENSE"`
| The collector and the UI only, for anything that already speaks OTLP/HTTP, including a Java application under the stock OpenTelemetry Java agent.
|===

[#agent]
== Agent

[source,bash]
----
java -javaagent:"$SENSE" -Dotel.service.name=my-app -jar build/libs/my-app.jar
java -javaagent:"$SENSE" -Dotel.service.name=my-app -cp build/classes/java/main com.acme.Main
----

The OpenTelemetry Java agent instruments the application, and a collector and UI start inside the same JVM on port 4000.
The agent exports to them over loopback.
Agent mode is one option, one process, and the UI at http://127.0.0.1:4000[].

`-Dspidersense.port=4001` moves the UI when 4000 is taken.
Spider Sense never prevents the application from starting: a failure in its own startup is logged to the application's stderr and swallowed.

[#forwarding]
== Agent, forwarding

[source,bash]
----
java -javaagent:"$SENSE" -Dspidersense.collector=http://127.0.0.1:4000 -jar app.jar
----

The instrumentation is the same as in agent mode, but no UI starts in the application's JVM.
The agent exports to a Spider Sense running elsewhere, so several applications can share one Spider Sense.

Use forwarding when two applications call each other, so that a trace crossing both arrives in one place.
Start the standalone Spider Sense first, then each application with `-Dspidersense.collector=` pointing at it.
Forwarding is also the right mode for a test task.
A test JVM is short-lived and may be forked more than once, and several embedded instances would fight over the port.

[#standalone]
== Standalone

[source,bash]
----
java -jar "$SENSE"
----

The collector and the UI run on port 4000 and nothing is instrumented.
Anything that speaks OTLP/HTTP can send to it: the two modes above, another language's SDK, or an OpenTelemetry Collector.
The standalone jar takes its properties as `--key=value` arguments as well as system properties, so `java -jar "$SENSE" --port=4001` is the same as `-Dspidersense.port=4001`.
It reads xref:configuration.adoc#properties-file[the properties file] too.

Two environment variables point an OpenTelemetry SDK at the standalone Spider Sense:

[source,bash]
----
java -jar "$SENSE" &
export OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4000
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
----

The protocol has to be `http/protobuf`, because there is no gRPC receiver.

[#other-languages]
=== Python, Node.js and Go

Python and Node.js have zero-code instrumentation, like the Java agent: a package installed beside the application instruments its web framework, HTTP clients and database drivers when the process starts.
Go has no such agent, so the application sets up the SDK in `main` and wraps its handler.
Each example below sends to a standalone Spider Sense on port 4000 under the service name `my-app`.

Python, with `opentelemetry-instrument` wrapping the usual command:

[source,bash]
----
pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install     # the instrumentation for every library installed

export OTEL_SERVICE_NAME=my-app
export OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4000
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED=true
opentelemetry-instrument --logs_exporter otlp python app.py
----

`opentelemetry-bootstrap` reads the packages already installed, so run it after the application's own dependencies.
The last variable and `--logs_exporter otlp` send the `logging` records as well; without them only traces and metrics arrive.

Node.js, with the instrumentation loaded by `--require`:

[source,bash]
----
npm install @opentelemetry/api @opentelemetry/auto-instrumentations-node

export OTEL_SERVICE_NAME=my-app
export OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4000
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_NODE_RESOURCE_DETECTORS=env,host,os,process
node --require @opentelemetry/auto-instrumentations-node/register app.js
----

Traces are exported by default, and the metrics and logs only when their exporter variable says `otlp`.
The last variable leaves out the cloud detectors, which otherwise probe a metadata server and print `MetadataLookupWarning` on a laptop.

Go, with the SDK set up in `main`:

[source,bash]
----
go get go.opentelemetry.io/otel \
       go.opentelemetry.io/otel/sdk \
       go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp \
       go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp
----

[source,go]
----
package main

import (
	"context"
	"log"
	"net/http"

	"go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
	sdktrace "go.opentelemetry.io/otel/sdk/trace"
)

func main() {
	ctx := context.Background()
	exporter, err := otlptracehttp.New(ctx) // reads OTEL_EXPORTER_OTLP_ENDPOINT
	if err != nil {
		log.Fatal(err)
	}
	tp := sdktrace.NewTracerProvider(sdktrace.WithBatcher(exporter)) // reads OTEL_SERVICE_NAME
	defer tp.Shutdown(ctx)
	otel.SetTracerProvider(tp)

	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("hello"))
	})
	log.Fatal(http.ListenAndServe(":8080", otelhttp.NewHandler(mux, "server")))
}
----

[source,bash]
----
OTEL_SERVICE_NAME=my-app OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4000 go run .
----

The exporter is the OTLP/HTTP one by construction, so Go needs no protocol variable.
`otelhttp` names each server span after the `ServeMux` pattern, so the Endpoints page shows `GET /hello` rather than one row for the whole server.
The queries appear only when the database calls make spans too, which in Go means wrapping `database/sql` with an instrumentation library, and in Python and Node.js happens for the drivers the packages above cover.

The receiver is the same for all three, so the pages, the findings and the CLI treat them as they treat a Java service.
The Java-only parts do not apply: the `code.stacktrace` of a slow query and the index catalog come from the Spider Sense jar's extension.

The same two variables make a Java application send to Spider Sense from any OpenTelemetry-compatible agent, not only the Spider Sense jar: the stock `opentelemetry-javaagent.jar` at a version of your own choosing, a vendor's distribution of it, or an agent already on the command line for another reason.

The stock agent is one jar, published on the project's https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases[GitHub releases] and on Maven Central as `io.opentelemetry.javaagent:opentelemetry-javaagent`.
The first line below fetches the latest release, and the second the version the Spider Sense jar bundles:

[source,bash,subs="attributes+"]
----
curl -LO https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar
curl -L -o opentelemetry-javaagent.jar https://repo1.maven.org/maven2/io/opentelemetry/javaagent/opentelemetry-javaagent/{otel-agent-version}/opentelemetry-javaagent-{otel-agent-version}.jar
----

[source,bash]
----
java -jar "$SENSE" &
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4000 OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
    java -javaagent:opentelemetry-javaagent.jar -jar app.jar
----

This setup lacks the defaults and the extension that the Spider Sense jar adds in agent mode: the endpoint and protocol set for you, a one-second export delay, the runtime metrics on, and `code.stacktrace` on slow queries (xref:design.adoc[Design]).
Everything else, the pages, the findings and the CLI, is the same, because it is the same data.
The extension is also what reads the index catalog of the tables a slow statement touches, so a finding's xref:findings.adoc#schema[schema block] exists only for a service that ran under the Spider Sense jar.
The receiver also accepts OTLP/JSON, so a shell can post a span with `curl`:

[source,bash]
----
curl -X POST http://127.0.0.1:4000/v1/traces \
     -H 'Content-Type: application/json' \
     -d @spans.json
----

xref:api.adoc#ingest[The HTTP API] gives the three ingest paths and what they answer.

Standalone is also how you read data after the application has gone.
The H2 file under `~/db/spider-sense/` outlives every process, so `java -jar "$SENSE"` opens the same screens on the same rows.

== The command line, the fourth way

[source,bash]
----
java -jar "$SENSE" findings --since=start
----

An argument that does not start with `-` is a command, and no server starts.
The command asks the running Spider Sense over HTTP, or reads the H2 file directly when none is running, and prints text.
xref:cli.adoc[The CLI] documents every command, and xref:agent-loop.adoc[The Loop] is how an AI agent uses them.

== Java versions

The jar itself needs Java 21 or later.
The monitored application can run on any JVM the OpenTelemetry Java agent supports, but the embedded UI needs 21 or later, so agent mode requires 21 or later.
For an application on an older JVM, run Spider Sense standalone and forward to it.

== Starting a JVM that is not `java -jar`

A build tool or a start script that forks the JVM has to pass `-javaagent` on to it.
For Gradle and Maven, xref:gradle-plugin.adoc[the Gradle plugin] and xref:maven.adoc[the Maven parameters] are the shortest route, and neither needs an absolute path in the build file.
The sections below are for everything else.

=== A start script from `installDist`

The script the Gradle `application` plugin generates passes `JAVA_OPTS` and `<APPNAME>_OPTS` to the JVM, so nothing in the build has to change.

[source,bash]
----
./gradlew installDist
JAVA_OPTS="-javaagent:$SENSE -Dotel.service.name=my-app" build/install/my-app/bin/my-app
----

`applicationDefaultJvmArgs` in `build.gradle` can also carry these arguments, but that edits the project.

=== Gradle `run`

The `run` task forks a JVM whose arguments come from the build, not from the shell, so either configure the task or avoid it.

[source,groovy,subs="attributes+"]
----
tasks.named('run') {
    jvmArgs '-javaagent:/absolute/path/to/spider-sense-{project-version}.jar', '-Dotel.service.name=my-app'
}
----

When the build file is not yours to edit, `./gradlew installDist` and the start script above are the cleaner route.

WARNING: `JAVA_TOOL_OPTIONS` works too, but every JVM the command starts picks it up, including the Gradle daemon, which then tries to host a Spider Sense of its own on port 4000.
Use `--no-daemon` with it, or give the daemon nothing to collide with.

== Knowing it worked

[source,bash]
----
java -jar "$SENSE" status
----

`status` names the mode (`agent` or `standalone`), the port, the OTLP endpoint, the database file and its size, the thresholds in force, the services seen and how many spans are stored.
The setup works when `counts.services` includes the application's service name and the span count grows after a request.
The UI at http://127.0.0.1:4000[] shows the same information to a person.

A restart also writes an automatic `start` mark for the service, so `marks` shows a new row with the note `pid <pid>` every time the application comes up.
`--since=start` therefore means the current run.
xref:marks-and-compare.adoc#marks[Marks] describes them.

== When it does not work

[cols="2,3",options="header"]
|===
| Symptom | Cause

| `status` says there is no Spider Sense at the url
| Nothing is running on that port, or the application was started on another one. Pass `--url=http://127.0.0.1:<port>`, or read the file directly with `--db=`.

| The application starts but `counts.spans` stays at 0
| The agent did not attach. `-javaagent:` was not on the JVM's own command line, which happens with a wrapper script, a container, or an IDE run configuration. Check the application's own stdout, where a failure in `premain` is logged.

| The service is called `unknown_service:java`
| No `-Dotel.service.name=` was set. Set it and restart.

| Port 4000 is already in use
| Another Spider Sense, or another application under the agent, has it. Use `-Dspidersense.port=4001` and `--url=http://127.0.0.1:4001`, or point the second application at the first with `-Dspidersense.collector=http://127.0.0.1:4000`.

| Two applications, and each trace stops at the service boundary
| Both are embedding their own Spider Sense. Put them in forwarding mode against one standalone.

| The application crashed and the UI went with it
| The CLI reads the H2 file directly and says so on stderr. `findings --since=start` still answers.

| A finding's `code` is empty or full of framework classes
| Only errors carry stack traces, and the package heuristic can guess wrong. Set `-Dspidersense.app.packages=com.acme`.

| The window is full of another run
| Windows default to `15m`. Use `--since=start`, or mark a moment and use `--since=<mark>`.
|===

When the application runs but Spider Sense collects nothing, the cause is in the configuration.
`status` and the application's stdout are where to look.

`scripts/demo.sh` and `scripts/demo-shared.sh` in xref:examples.adoc[The Examples] run these modes for real: `demo.sh` starts four applications each with its own embedded Spider Sense, and `demo-shared.sh` forwards the same four to one standalone.
